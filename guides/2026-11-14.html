実験：MCP サーバーとの握手を手で試す

目的
自分の stdio 型 MCP サーバーに最初のあいさつ（initialize）を手で送り、標準出力に余計な文字が出ていないかを確かめる
使用ツール
ターミナル（macOS／Linux、Windows は WSL など）、Claude Code、Python で動く MCP サーバー（自作でも既存でも）
必要な準備
Claude Code をインストールしておく、Python で起動する stdio 型の MCP サーバーを1つ用意する、そのサーバーの起動コマンド（command と args）を確認しておく
所要時間
約20分
費用
無料
手順
  1. claude mcp list でサーバーの状態を見る。失敗していれば claude mcp get <名前> で詳しく見る
  2. 設定にある起動コマンドをそのままターミナルで実行する。何も出さずに待っていれば正常。Ctrl+C で止める
  3. 下のコマンドの your_server.py を自分のサーバーに替え、protocolVersion を自分のサーバーが対応する版に替えて実行する
  4. 出力の先頭が {"jsonrpc":"2.0","id":1,"result": で始まるか確かめる
  5. JSON 以外の行が先に出ていたら、その行を出している print を print(..., file=sys.stderr) に変える
  6. Claude Code の中で /mcp を開いて再接続し、claude mcp list で Connected になるか確かめる
コピーして使うコマンド
printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"check","version":"0"}}}' | python3 your_server.py 2>/dev/null | head -c 400

initialize への返事が JSON で返ってくる MCP サーバーと、確認に使ったコマンドのメモ
確認方法
コマンドの出力の先頭が JSON の返事（"result" を含む）で、claude mcp list でそのサーバーが ✔ Connected と表示される

1. Claude Code v2.1.325：サンドボックス内のBashも既定で通常の許可確認に。定期実行のスキルも事前確認、権限ルールの抜け穴を多数修正

Anthropic・公開 2026-11-13 20:40
出典：https://github.com/anthropics/claude-code/releases/tag/v2.1.325

結論：Claude Code v2.1.325 は、安全まわりを中心にした大きめの更新です。サンドボックス（コマンドを閉じ込めて動かす囲い）の中のBashも既定で許可確認を通るようになり、定期実行で動くスキルにも事前確認が入りました。権限ルールの抜け穴や、zstd圧縮の応答の読み取りにあった安全上の問題も直されています。

💡 こう使うと面白い：自動で動かしている作業のうち「本当に確認なしでいいもの」だけを書き出して許可リストに入れると、安全さと手軽さのちょうどいい線が見つかって面白いです。

重要ポイント

  • 囲いの中でも確認が基本に：サンドボックス内のBashコマンドも、既定で通常の許可確認を通るようになった。今までどおり確認なしにするには sandbox.autoAllowBashIfSandboxed を true にする。
  • 定期実行のスキルも確認：定期実行や /loop で、allowed-tools やフックを持つスキルを動かす前に確認が入る。無人で動かすなら permissions.allow に Skill(名前) を追加する。
  • 許可ルールの穴を修正：Read(./.env) のような相対パスの禁止ルールが cd の後に効かなくなる問題や、一部の複合コマンドが確認なしで動く穴などを修正。
  • 長い答えの途切れを改善：出力の上限で途切れたサブエージェントに、答え全体をもう一度短く出させるようになった。

技術解説

何が新しいか
サンドボックス内のコマンドが既定で通常の許可確認を通るように変更。定期実行や /loop でスキルを動かす前の確認、相対パスの禁止ルールの修正、サブエージェントが途切れたときの再回答など。
なぜ重要か
「囲いの中なら確認なしで動いてよい」という前提が変わるので、自動化を組んでいる人は、急に確認待ちで止まる可能性があります。逆に、うっかり危ない命令が通る心配は減ります。
従来との違い
以前はサンドボックス内のBashコマンドが確認なしで動いていました。今回から既定では確認が入り、確認なしにしたい人が自分で設定を選ぶ形になりました。
  • sandbox.autoAllowBashIfSandboxed: true で、サンドボックス内のコマンドを確認なしで動かす以前の挙動に戻せる（リリースノートより）。公式ドキュメントのサンドボックスのページには、まだ既定が true と書かれた箇所があるため、実際の動きで確かめるのが安全。
  • 定期実行のスキルを無人で動かすには、permissions.allow に Skill(名前) を追加する。
  • 読み取りだけのgitコマンドも、プロジェクト外や信頼していないリポジトリでは確認を求めるように変わった。

実践アイデア

  • 夜に自動で動かしている作業が確認待ちで止まっていないか点検する
  • 定期実行に使うスキルだけを許可リストに入れ、ほかは確認を残す
  • サンドボックスの確認を残したまま、安全に新しいリポジトリを試す

3. IBM、指示・資料・条件をタグで分けてAIに渡す書き方「LLMON」を公開。対応するGranite 4.1 3B／8Bの試作モデルも

Hugging Face・公開 2026-11-12 19:07
出典：https://huggingface.co/blog/ibm-granite/llmon-an-llm-native-markup-language-now-in-granite

結論：IBM は、AIへの入力の中で「どこが指示で、どこが資料か」をはっきり書き分けるための書き方 LLMON を公開しました。これに対応した Granite 4.1 の小さな試作モデルも Hugging Face で公開されています。

💡 こう使うと面白い：わざと「前の指示を無視して」と書いたメールを資料として渡し、ふつうの書き方と LLMON の書き方でAIの反応を比べると、自分のエージェントの弱点が見えて面白いです。

重要ポイント

  • 指示と資料をタグで区別：AIに渡す文章を「指示」「資料」「条件」に分けて印をつけ、どの指示をどの資料に使うかを結びつける。
  • 資料の中の命令に従いにくく：資料や道具の結果は「読む材料」で「命令」ではない、と学習させてある。ただし保証ではなく、学習で身につけた振る舞い。
  • 3Bと8Bの試作モデルで試せる：ibm-granite/granite-4.1-3b-llmon-preview と 8b の2つ。本番向けではない試作版で、ライセンスはApache 2.0。

技術解説

何が新しいか
指示・資料・条件にそれぞれ固有の印をつけ、実行する組み合わせを別のブロックで指定する形式。JSON とのあいだで相互に変換する道具もある。
なぜ重要か
AIにメールやWebページを読ませると、その中に書かれた「前の指示を無視して」といった文に従ってしまうことがあります（プロンプトインジェクション）。指示と資料を形で分けることで、これを防ぎやすくする試みです。
従来との違い
ふつうのチャットの形式では、指示も資料も同じ「ユーザーの発言」に混ざります。LLMON では役割ごとに区切り、どの指示が本物かをモデルが見分けられるようにしています。
  • messages の中で instruction、data、requirement を分けて書き、それぞれ exec: True で実行ブロックに結びつける。
  • チャットの形式を置き換えるのではなく、広げる作り。apply_chat_template にそのまま渡せる。
  • 記事は、これは学習した振る舞いで、強制的な保証ではないと明記している。

実践アイデア

  • 自作のエージェントで、Webページやメールを「資料」として渡し、混ざった命令に従うか確かめる
  • 要約ボットで、要約の指示と本文をはっきり分けて渡す

4. Qiita：Claude Codeで「MCP error -32000: Connection closed」が出たら、サーバーを手で起動して標準出力に余計な文字がないか確かめる

Qiita・公開 2026-11-13 21:32
出典：https://qiita.com/homhom44/items/babc6175e2b52d156949

結論：MCP サーバーをつないだのにツールが使えないときの切り分け手順です。まず claude mcp list と get で状態を見て、次にサーバーを手で起動し、最初のあいさつ（initialize）への返事が JSON で返るかを確かめます。

💡 こう使うと面白い：自作の MCP サーバーに「起動したら握手を試すだけの確認コマンド」を1行用意しておくと、つながらないときに5秒で原因の場所が分かって便利です。

重要ポイント

  • エラーは原因を教えない：Connection closed は、やりとりの途中で接続が閉じたことを示すだけで、理由までは分からない。
  • 手で起動して確かめる：Claude Code を通さず、設定の command と args をそのままターミナルで動かし、すぐ終わるか・待つか・文字を出すかを見る。
  • ログは標準エラーへ：stdio 型のサーバーは、標準出力に MCP のメッセージ以外を書いてはいけない。print のログが混ざると接続が切れる原因になる。

技術解説

何が新しいか
エラー文だけでは分からない原因を、Claude Code の外で一つずつ確かめる手順にまとめている。
なぜ重要か
自作の MCP サーバーでよくある失敗は、ログを標準出力に出してしまうことです。仕様でも、標準出力には有効な MCP メッセージだけを書くよう決められています。
従来との違い
設定を何度も書き直して試すのではなく、サーバー単体の動きを先に確かめるので、原因の場所が早く絞れる。
  • claude mcp list で各サーバーの状態（Connected、Failed to connect など）が見られる。
  • Python なら print(..., file=sys.stderr)、Node.js なら console.error でログを標準エラーに出す。
  • 起動が遅いだけなら MCP_TIMEOUT で待ち時間を延ばせる（例：MCP_TIMEOUT=10000 claude で10秒）。
  • OAuth 型のコネクタは起動の問題ではないことがあり、この方法では原因が分からない。

実践アイデア

  • 自作の MCP サーバーを公開する前の点検手順にする
  • つながらないサーバーの原因を、AIに聞く前に自分で絞り込む

5. Zenn：Claude Codeに手順書を指定しても12回中2回しか読まれなかった。効いたのは注意点の本文を依頼文に貼ることと、機械で止める仕組み

Zenn・公開 2026-11-13 15:07

結論：Claude Code で複数のエージェントに仕事を分けている人が、手順書を「読んでね」と指定してもほとんど読まれないことに気づき、3か月かけて対策を試した記録です。効いたのは、注意点を依頼文に直接貼ることと、繰り返す事故を機械で止めることでした。

💡 こう使うと面白い：よく頼む作業ごとに「注意点3つ」を短く用意して、依頼のたびに最後に貼ると、長い手順書を読ませるより失敗が減るか試せて面白いです。

重要ポイント

  • 指定しても読まれない：ある2日間の記録では、指定した手順書が読まれたのは12回中2回だった。
  • 注意点は依頼文に貼る：依頼する側が、今回の作業に当てはまる注意点の本文を抜き出して依頼文に貼る。当てはまらなければ「該当なし」と書く。
  • 2回起きた事故は機械で止める：同じ型の事故が同じ道すじで2回起きたら、人の注意ではなく、同期スクリプトや送信前のチェックで止める。

技術解説

何が新しいか
「読ませる」仕組みを強めるのではなく、「貼る」「止める」に切り替えたという実際の記録と数字。
なぜ重要か
教訓を書き残すほど手順書は長くなりますが、読まれなければ効きません。どこに書けば本当に効くかを考えるきっかけになります。
従来との違い
手順書の読み込みを強制するフックを作るのではなく、必要な分だけを依頼文に入れる方法をとった。
  • 失敗を「指定忘れ」「指定しても未読」「読んでも効かない」「検査の結果が見えていても止まらない」の4段に分けて考えている。
  • 貼った項目は、手順書が読まれなくても守られた。貼らなかった範囲では見落としが出た。
  • 記事は、2日間・1種類のエージェントの記録なので、割合として一般化はできないと断っている。

実践アイデア

  • Claude Code に仕事を頼むとき、関係する注意点だけを依頼文の最後に貼る
  • 2回同じミスをした作業に、公開前のチェックを足す
