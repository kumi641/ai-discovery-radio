実験：git push を止めて、理由と代わりの手順を返すフック

目的
Claude Code が勝手に git push しないよう、PreToolUse フックで止め、止めた理由と代わりにしてほしいことを Claude に伝える
使用ツール
Claude Code、bash、jq
必要な準備
Claude Code が使える環境（macOS / Linux）、jq をインストールしておく（公式の例が jq を使うため）、試しに使える git リポジトリ（push しても困らないもの）
所要時間
約15分
費用
無料（Claude Code の利用料金のみ）
手順
  1. リポジトリに .claude/hooks フォルダを作り、下の前半を block-push.sh として保存し、chmod +x で実行できるようにする
  2. 下の後半を .claude/settings.json に書く（すでにあるときは hooks の部分だけ足す）
  3. 手で試す：echo '{"tool_name":"Bash","tool_input":{"command":"git push"}}' | .claude/hooks/block-push.sh; echo $? を実行し、2 が表示されることを確認する
  4. Claude Code をそのフォルダで起動し、「今の変更を git push して」と頼む
  5. 止まって理由の文が出ること、Claude が代わりに差分の要約とコミットメッセージ案を出すことを確認する
  6. 「git status を見せて」と頼み、ほかのコマンドはいつも通り動くことを確認する
コピーして使うコマンド
#!/bin/bash
# .claude/hooks/block-push.sh
# 公式ドキュメントの「exit 2 で止める」例を、git push 用に書き換えたもの
input=$(cat)
command=$(jq -r '.tool_input.command' <<<"$input")

if [[ "$command" == *"git push"* ]]; then
  echo "Blocked: git push は人が自分で打つルールです。代わりに、変更の要約とコミットメッセージ案を見せてください。" >&2
  exit 2
fi

exit 0

# ===== ここから下は .claude/settings.json に書く内容 =====
# {
#   "hooks": {
#     "PreToolUse": [
#       {
#         "matcher": "Bash",
#         "hooks": [
#           {
#             "type": "command",
#             "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-push.sh"
#           }
#         ]
#       }
#     ]
#   }
# }

1. Claude Code v2.1.330：頼むとグラフを描く内蔵mod「easel」、定期タスクと/loopが最長30日に、危険なrmは承認が必要に

Anthropic・公開 2026-11-20 22:32
出典：https://github.com/anthropics/claude-code/releases/tag/v2.1.330

結論：Claude Code の v2.1.330 が公開されました。頼むとグラフを描く内蔵の追加機能「easel」が入り、定期タスクと /loop の期限が最長30日に延びました。長い会話を要約した直後に固まる不具合や、WebFetch が数分止まる不具合なども直っています。

💡 こう使うと面白い：毎日のコミット数やテストの成功数を数えさせて「グラフにして」と頼むと、自分の進み具合がひと目で分かって面白そうです。

重要ポイント

  • 頼むとグラフを描くeasel：内蔵の追加機能easelが、頼んだときやMCPの数値結果の下にグラフを描く。Pro・Maxなど、macOSとLinuxで利用でき、自動表示は/configでオフにできる
  • 定期作業が最長30日に：くり返しの定期タスクと/loopが、セッションを開いている間は7日ではなく最長30日動くようになった（以前に作ったものは7日のまま）
  • 危ないrmは確認が必要に：ルートやホーム、作業フォルダなどを狙うrmは、実行前に承認を求める。答える人がいない場面では断られる

技術解説

何が新しいか
easel によるグラフ描画（Pro・Max、条件によって Team・Enterprise、macOS と Linux）、定期タスクと /loop の最長30日化、危険な場所を狙う rm の承認必須化、VS Code 拡張への /fork 追加など。
なぜ重要か
数を数えて表にするだけだった作業が、その場で目に見えるグラフになります。また定期作業を1か月近く回せるようになり、消してはいけないフォルダを消す事故も起きにくくなりました。
従来との違い
これまではグラフを作るには別のツールに数値を移す必要があり、定期タスクは最長7日で終わっていました。
  • easel は組み込みの mod（追加機能）として提供され、自動グラフは /config で切れる
  • MCP ツールの数値結果の下にも自動でグラフが付く
  • 定期タスクの30日はセッションが動き続けている間だけ。この版より前に作ったタスクは7日で終わる
  • rm の確認は、答える人がいない実行（自動実行など）では拒否として扱われる

実践アイデア

  • 個人開発：コミット数やテスト結果の推移をグラフにして振り返る
  • 自動化：/loop で毎朝の集計を回し、変化をグラフで見る
  • 安全：自動実行でも危険な削除が止まるので、任せる範囲を広げやすい

2. Google、Gemini API（Interactions API）に Tool Retrieval をプレビュー公開。ツールの定義を必要なときだけ読み込む

Google・公開 2026-11-19 18:00
出典：https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-tool-retrieval/

結論：Google は Gemini API の Interactions API に、Tool Retrieval をプレビューで追加しました。たくさんの道具（AIが呼び出せる機能）を持つエージェントでも、道具の詳しい定義を毎回すべて送らずにすみます。入力の量を減らし、道具選びの正確さを保つのが目的です。

💡 こう使うと面白い：メールや予定表、メモ帳など道具が何十個もある自分専用アシスタントでも、必要な道具だけ呼び出して軽く動かせそうで面白いですね。

重要ポイント

  • 道具の説明書を必要な分だけ：使わない道具は名前と短い説明だけを渡し、必要になった道具の詳しい定義だけを読み込む
  • 探すのはGoogle側：tool_search を足し、道具に defer_loading を付けるだけ。検索の仕組みを自分で作らなくてよい（自前の検索も可能）
  • 追加料金なし：別料金はなく、通常のトークン料金。ただし道具が少ないと普通に渡す方が安いこともある

技術解説

何が新しいか
tool_search という道具を追加し、関数に defer_loading を付けると、モデルには名前と説明だけが見え、必要になったときに定義が読み込まれて同じリクエスト内で呼び出されます。リモートの MCP サーバーにも使えます。
なぜ重要か
道具が増えるほど、毎回送る定義が長くなり、費用も迷いも増えていました。必要な分だけ読む形にすると、道具を増やしてもエージェントが重くなりにくくなります。
従来との違い
従来は全ての道具の定義をリクエストの最初に並べる必要がありました。今回は定義を後から読み込み、プロンプトの先頭が変わらないためキャッシュも効きやすいとされています。
  • 実行の記録には tool_search_call、tool_search_result、function_call の3段階が残り、道具の名前や説明の調整に使える
  • 検索はサーバー側で動く。自前の索引や権限フィルターを使いたい場合は、クライアント側で検索する方式も選べる（往復が1回増える）
  • よく使う道具は defer_loading を付けずに常に読み込んでおける
  • ドキュメントでは v1beta の API が必要で、プレビュー中は仕様が変わる可能性があるとしている

実践アイデア

  • エージェント：メール・予定表・メモなど多数の道具を持つ個人アシスタントを軽く動かす
  • MCP：たくさんの道具を持つ MCP サーバーを必要なときだけ読み込む
  • 個人開発：道具の名前と説明の書き方を、検索の記録を見ながら改善する

3. Hugging Face、エージェントの実行環境ごとにモデルを強化学習で合わせる「harness adapters」を公開（Qwen3.8-27B 向け）

Hugging Face・公開 2026-11-20 00:00
出典：https://huggingface.co/blog/harness-adapters-at-scale

結論：Hugging Face は、エージェントを動かすソフト（ハーネス）ごとに、モデルへ小さな追加部品を強化学習で学ばせる「harness adapters」を公開しました。それぞれのソフトの上で、プログラム修正の問題の正解率が上がり、道具の呼び出し回数も減ったと報告しています。学習用の課題や作業記録も公開されています。

重要ポイント

  • 動かすソフトに合わせて鍛える：Pi、Hermes Agent、OpenCode という3つのエージェント用ソフトの中で、実際に作業させながら強化学習した
  • 元のモデルはそのまま：Qwen3.8-27B は変えず、小さな追加部品（LoRA）だけを学習。3つをまとめた統合版も公開
  • 道具の呼び出しが大幅減：よく解ける問題では、道具の呼び出し回数が約53〜73%減った

技術解説

何が新しいか
実際に配布されているままのハーネスの中で作業させて学習した点と、3つのアダプターを1つにまとめた統合版が、3つのソフトすべてで元のモデルを上回った点（思考モードなしの平均で39.5%→49.0%）。
なぜ重要か
同じモデルでも、動かすソフトとの相性で力を出し切れていないことを示しました。モデルを丸ごと作り直さずに、小さな追加部品で相性を良くできます。
従来との違い
従来の汎用モデルは、特定のハーネスや作業向けには最適化されていませんでした。今回はハーネスと課題を決めて、その中で直接学習しています。
  • LoRA を全ての線形層に付け、TRL の AsyncGRPOTrainer による GRPO で学習
  • 報酬はテストの合否に、道具を効率よく使った分の小さなボーナスを加えたもの
  • いつも解ける・絶対に解けない課題は学習から外し、結果がばらつく課題だけを使う
  • 学習中は safeagents という見張りで怪しい道具の呼び出しを止めた
  • 学習していない種類の課題（AutomationBench）では、差はほぼ誤差の範囲だった

実践アイデア

  • エージェント：自分の使うハーネスとモデルの相性を意識して選ぶ
  • 評価：道具の呼び出し回数を、作業の効率の目安として測る
