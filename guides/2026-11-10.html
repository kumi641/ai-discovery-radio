手順
  1. 練習用フォルダーを作って移動し、ダミーの .env（例：DUMMY_TOKEN=not-a-real-secret）と、1行目に「hello」と書いた README.md を作る。本物の鍵は絶対に入れない

  5. claude --settings .claude/settings.restricted.json -p "README.md の1行目を教えて" を実行し、hello が返ることを確認する（通すべきものが通る）

1. Anthropic、Claude Fable 5.2 と Claude Mythos 5.2 を発表

Hacker News・公開 2026-11-09 18:56
出典：https://www.anthropic.com/claude-fable-and-mythos-5-2

重要ポイント

  • 同じ基盤モデルの2系統：Fableは安全対策を強めて一般提供、Mythosは検証プログラムを通った組織向け。
  • コード・推論・視覚が向上：出力速度はFable/Mythos 5.1より最大30%速いと公式が説明。
  • $8/$40 per Mtok：入力100万トークン8ドル、出力40ドル。fast modeは16ドル/80ドルで生成が最大2.5倍速。
  • 普段使いはOpus 5.5推奨：公式は多くの作業はOpus 5.5から始め、野心的で先の見えない課題でFableへ、と推奨。

技術解説

何が新しいか
Fable/Mythosの5.2世代。Fable 5.2はAWS・Google Cloud・Azureを含む全プラットフォームで提供され、モデルIDは claude-fable-5-2。
なぜ重要か
難しい長時間タスク向けの選択肢が更新された。Fable 5.1よりブロックされるリクエストが約55%減ったとされ、正当な作業で止まりにくくなった。
従来との違い
Anthropic自己申告のベンチマークでは、エージェント型コーディング（FrontierSWE v2 69.9%）などでOpus 5.5を上回る。一方で料金はOpusより高い上位モデルという位置づけ。
  • FableとMythosは同じ基盤モデルで、提供範囲と安全対策が異なる
  • fast modeは料金2倍で生成速度が最大2.5倍
  • 推論の強さ（effort）を low〜max で選べ、llm-anthropic でも指定できる

実践アイデア

  • 大きなコードベースの設計見直しなど、難度の高いエージェント作業
  • 同じお題をeffort別に比べ、自分の用途に必要な強さを見極める
  • SVGなどコードで描くクリエイティブ生成の品質比較

2. Claude Code v2.1.321：Fable 5.2 を既定のFableに、MCP OAuthやサンドボックスの修正

Anthropic・公開 2026-11-09 19:22
出典：https://github.com/anthropics/claude-code/releases/tag/v2.1.321

重要ポイント

  • Fable 5.2が既定のFableに：claude-fable-5-2を追加。1M context、$8/$40、cache read $0.20 per Mtok。
  • MCP OAuthの秘密漏れを修正：サーバーがリダイレクトした際、refresh tokenなどを別ホストへ送る問題を修正。
  • サンドボックス外実行を修正：読み取り専用Bashコマンドが確認なしでサンドボックス外で動くケースを修正。
  • remote-controlに--settings：起動する全セッションに同じsettingsファイルを適用できる。

技術解説

何が新しいか
Fable 5.2対応、claude remote-control の --settings <file>、cp/mv先のファイルへのdenyルール適用など権限チェックの修正。
なぜ重要か
MCPやリモート操作を使う人にとって、秘密情報の扱いと権限チェックの穴が塞がれた更新。新モデル以上に、更新しておく価値がある。
従来との違い
remote-controlで起動するセッションにも、ファイル1つで同じ設定（権限ルールなど）を一括で当てられるようになった。
  • MCP OAuthのリダイレクト時に秘密を別ホストへ送らないよう修正
  • cp や mv でディレクトリに書くファイルにも deny ルールと保護ファイルの確認が効くよう修正
  • settingsファイルが変わっても、remote-controlを再起動するまで新セッションは始まらない

実践アイデア

  • MCPサーバーを使うエージェント環境の安全性向上
  • remote-controlで複数セッションを動かす自動化に共通の権限設定を適用
  • Fable 5.2を難しいリファクタリングに使う

3. Simon Willison：エージェントが書いたPR説明を <details><summary> に隠し、人が選んだ短い冒頭を置く

Simon Willison・公開 2026-11-09 04:25
出典：https://simonwillison.net/2026/Nov/9/details-summary/

重要ポイント

  • エージェントのPR説明は長すぎる：正確で網羅的だが、読まれず“slop”のように見えてしまう。
  • 冒頭に人が選んだ短い説明：読者がすぐ状況をつかめる最短の文。必要ならスクリーンショットも。
  • 全文は<details>に格納：情報は失わず、読みたい人だけ開ける。
  • <summary>にモデル名：例：Claude Opus 5.5 Medium のように、書いたモデルとeffortを示す。

技術解説

何が新しいか
エージェントの出力を消さずに、人の編集判断を先頭に置くというPR説明の型。
なぜ重要か
エージェントにPRを作らせるほど、読む側の負担が増える。冒頭の数行を人が責任を持って書くことで、レビューの入口が軽くなる。
従来との違い
従来はエージェントの説明をそのまま貼るか、人が全部書き直していた。この方法は全文を残したまま、読む順序だけを整える。
  • GitHubのMarkdownは <details> と <summary> による折りたたみを公式にサポート
  • <details open> にすると最初から開いた状態で表示される
  • <summary> にモデル名とeffortを書いて出所を明示する

実践アイデア

  • Claude Codeが作るPRのテンプレート化
  • エージェントの作業ログを残しつつ短い要約を先頭に置く運用
  • 個人プロジェクトの変更履歴を後から読みやすくする

4. Zenn：新人にClaude Codeを渡すための制限付き起動ラッパーと権限設計（--restrictedは社内名）

Zenn・公開 2026-11-09 23:00
出典：https://zenn.dev/joinclass/articles/restricted-ai-20261108220018-28240

重要ポイント

  • 読む・書く・外に出すの3段階：読む＝許可、書く＝確認つき、push・削除・送信など＝禁止。
  • 秘密を読ませないが最優先：読んだ内容はプロンプトに乗るため、書き換え防止より重要。
  • --restrictedは公式でない：社内ラッパーの名前で、中身は --settings など公式オプションで構成。
  • 効いているか必ず検証：止まるべきものが止まり、通るべきものが通るかを claude -p で確認。

技術解説

何が新しいか
権限設計を「設定ファイル＋起動ラッパー＋検証スクリプト＋リポジトリ側の保護」の4層で組む実務的な型。
なぜ重要か
事故の原因はAIの性能ではなく渡した権限の広さ、という整理が明快。個人開発でも、秘密ファイルやpushを設定で止めておけば安心して任せられる。
従来との違い
本人の注意力に頼らず、設定ファイルで制限を担保する。さらに「全部止まったら設定が読み込まれていない可能性」と、検証の落とし穴まで扱っている。
  • settingsの permissions で allow / ask / deny を書き分ける
  • Bashのルールは書式に注意（記事では Bash(git push) だけでは git push origin main を止められないと指摘）
  • 相対パスだと別ディレクトリから起動したとき読み込まれないことがある
  • ユーザー設定とマージされるため、個人設定の広いallowが残っていないか確認する

実践アイデア

  • 個人のエージェント環境で秘密ファイルとpushを封じる
  • 外注や共同作業者向けの安全な起動設定
  • 自動化ジョブ（claude -p）の権限を最小にする
