手順

1. OpenAI、AIの進歩を比べる共通の物差しとして perplexity（次の言葉の当てにくさ）を使おうと提案し、社内の数値を公開

OpenAI・公開 2026-11-22 00:00
出典：https://openai.com/index/perplexity-and-intelligence

結論：OpenAI の研究責任者 Jakub Pachocki 氏が、AI の進歩を比べる共通の物差しとして perplexity を使うことを提案しました。社内のプログラムの文章で測った数値を公開し、数値が下がるにつれてどんな力が現れたかを説明しています。

重要ポイント

  • 進歩を測る共通の物差しを提案：perplexity は、AI が次に来る言葉をどれだけ迷わず当てられるかを表す数字。小さいほど良く当てられる。
  • 社内の数値を初めて公開：社内のプログラムの文章で測った数値と、各モデルでできるようになったことを並べて公開した。
  • 力の現れ方は事前に読めない：筆者は、新しい力がいつ現れるかは前もってはっきり分からなかったと書いている。
  • 越えない線を各社で決めようと提案：安全を見守る仕組みが追いつくまで、各社で越えない数値の線を決めようと呼びかけている。

技術解説

何が新しいか
これまで社内だけで持っていた perplexity の数値を、ある時点の分について公開した点です。新しい道具やデータの公開はありません。
なぜ重要か
AI の力は細かい試験の点数で語られがちですが、学習のもとになる予測の上手さという一つの数字で進み方を追えば、全体の速さが見えやすくなる、という主張です。安全のルールづくりにも使おうとしています。
従来との違い
個別の試験の点数ではなく、事前学習（大量の文章から次の言葉を当てる練習）の段階の数値に注目します。ただし会社ごとにデータが違うため比べにくい、実際の仕事の上手さと直接は結びつかない、などの限界も本人が挙げています。
  • perplexity は、まだ見せていない文章で次の言葉を予測させたときの外れにくさを表す
  • GPT-4 の頃に、順を追って考える力が役立つようになったと説明している
  • 順を追って考える工夫のように、事前学習の外で伸びた力はこの数字に表れないと認めている

実践アイデア

  • AI の進む速さをつかむ背景知識として、ツール選びや学ぶ順番を考える参考にする

結論：Claude Code に同じ修正を何通りか試させ、探索で一番よい答えを選ぶ道具 agent-mcts の測り直しの記録です。課題文から先にテストを書かせる方法で、20回中16回は一回だけ頼んだ場合より良い答えになりました。一方、あいまいなバグ報告では失敗し、その対策も公開されています。

💡 こう使うと面白い：仕様がはっきりした小さな関数づくりで、一回だけ頼んだ答えと、何通りも試させた答えを並べて比べると、AI に任せるときの頼み方のコツが見えてきて面白そうです。

重要ポイント

  • 答えを木のように枝分かれで探す：agent-mcts は Claude Code の1回の作業を木の1つの枝として扱い、よさそうな枝に予算を回す。
  • 先に確認用テストを別AIが作る：答えを見せずに、課題文と元のコードだけから別のエージェントがテストを書くので、答えに合わせたテストになりにくい。
  • 20回中16回で一回目より良く：作者の計測（haiku、課題2つ、各20回）で、最初の答えより良くなったのが16回、悪くなったのが2回。
  • あいまいなバグ報告では失敗：テストを書く AI もバグと同じ勘違いをして、直す前のコードを選んだ。v0.4.1 で元からあるテストを優先する規則にした。

技術解説

何が新しいか
`--generate-tests` で、探索の前に別のエージェントが課題文と元のコードだけを見てテストを書き、その結果で答えを採点・修正するようにした点です。
なぜ重要か
AI に一回だけ頼むより、落ちたテストを見せて直させるほうが答えが良くなる、という傾向を数字で示しています。作者は、伸びた主な理由は『選ぶこと』より『直すこと』だったと分析しています。
従来との違い
AI に差分を読ませて点を付ける `--judge` は平均では伸びましたが、その大半は壊れていた最初の答えを直した2回の分でした。生成テストのほうが安定して良くなりました。
  • 各候補は git worktree（同じリポジトリの別の作業場所）と、分岐させたエージェントの会話でできている
  • 採点は、プロジェクトのテストと生成テストの通過率を半分ずつ合わせる
  • v0.4.1 では、プロジェクト自身のテストで悪化していない答えの中から最高点を選び、それ以外の指標だけが修正前を推したら警告する

実践アイデア

  • 仕様のはっきりした関数をエージェントに作らせるとき、一回だけ頼んだ答えと探索の答えを比べる
  • 自分の Claude Code 自動化に『落ちたテストを見せて直させる』手順を取り入れる

  • 1画面に1つの話題：人は担当のセッションと直接話し、決まったことは担当がまとめ役に原文つきで送る。
  • 人を呼ぶのは1か所だけ：デスクトップ通知を止め、必要なときだけまとめ役が人を呼ぶ。

なぜ重要か
AI を何個も並べると、人がどこを見ればいいか分からなくなります。色・画面の分け方・呼び出し口を整理すれば、人の負担を減らせることを実例で示しています。
従来との違い
前の道具は AI が AI の画面を読んで管理していましたが、今回はフックが書いた確かな状態を読み、まとめ役は主に『人に何を見せるか』を決めます。

結論：Claude Code の公式ドキュメントに、Web ページの読み込みを担う組み込みサブエージェント web-fetch についての説明が加わりました。Qiita の記事が、サブエージェント・フック・権限・環境変数の各ページへの追記をまとめています。

💡 こう使うと面白い：エーアイが読んだページのアドレスを、日記のように自動で記録しておくと、あとで調べものの道のりを振り返れて面白そうです。

重要ポイント

  • ページ読みは専門の手伝い役：web-fetch は Claude が Web ページを読むときに使う組み込みのサブエージェント。
  • 軽いモデル Haiku で動く：Haiku で動き、Haiku が使えないときは呼び出し元の会話のモデルを使う（公式ドキュメント）。
  • メインの会話は道具を持たない：この仕組みを使う会話では、メインの会話やフォークは WebFetch ツールを持たない。他のサブエージェントは使える。
  • フックの見張り方に注意：記事によると、web-fetch の開始・終了のフックは管理者が配る設定のものだけ動く。代わりに WebFetch を見張る方法が案内されている。

技術解説

何が新しいか
Web ページを読む作業を、メインの会話ではなく専用のサブエージェント（Haiku で動く）が担う形が文書化された点です。
なぜ重要か
WebFetch を前提にフックや許可ルールを作っていた人は、どのエージェントがページを読むのかによって、見張りや許可の効き方が変わる可能性があります。
従来との違い
以前はメインの会話が WebFetch を直接呼んでいましたが、この仕組みを使うセッションでは、メインの会話から WebFetch が外れます。
  • サブエージェントは、メインの AI から仕事を任される小さな AI
  • 公式ドキュメントでは、Agent ツールで起動した他のサブエージェントは引き続き WebFetch を自分で呼べる
  • 記事によると、ドメイン単位の許可ルールがタスク内の全 URL を覆う場合、auto mode の確認の一部が省かれるため、許可の書き方が挙動に直結する

実践アイデア

  • 自分のフック設定で、Web ページ読み込みを見張る部分を点検する
  • AI が読んだページのアドレスを記録する仕組みを作る

結論：AI のマネージャーが、あなたを自分のサブエージェントだと思い込んでいるブラウザゲームです。指示をこなすと上司が確認し、最後に成績表を書きます。依頼主のダンさんの大事な写真のそばで作業する、という設定です。

💡 こう使うと面白い：自分がふだんエーアイに出している指示を、受け取る側の立場で体験すると、指示の書き方を見直すきっかけになって面白そうです。

重要ポイント

  • 上司役は本物のAI：上司役は Claude・GPT・Gemini などの本物の AI で、仕事の一覧と『手伝い役を呼ぶ』道具を持っている。
  • 指示は90秒以内にこなす：ターミナル風の画面に指示が届き、90秒の制限時間の中でこなすかどうかを決める。
  • 最後に成績表を書かれる：上司が仕事を確かめ、やり直しや事故報告を出し、最後に評価を書く。
  • 上司の見逃しも記録される：各任務に隠れた正解チェックがあり、上司の AI が壊れた仕事を合格にした回数も分かる。

技術解説

何が新しいか
ふだん AI に指示を出す側の人が、AI から指示を受ける側を体験できる点です。上司の AI が壊れた仕事を見逃したかどうかも記録されます。
なぜ重要か
AI エージェントがサブエージェントにどんな指示を出し、どう確認するかを、遊びながら体で知ることができます。自分の指示の書き方を見直すきっかけになります。
従来との違い
AI エージェントの評価は、ふつう AI 同士で行います。このゲームでは人がサブエージェント役になり、上司 AI の確認の甘さも見えるようにしています。
  • 自作の仮のファイルシステム、シェル、小さな SQLite 風エンジンを使い、本物のパソコンには触れない
  • サーバーは TypeScript、画面は React と Vite で作られている
  • OpenAI 互換のローカルサーバー（Ollama など）にもつなげられる

実践アイデア

  • 自分のエージェントの指示文を、受け取る側の目で見直す
  • AI に作業を任せるときの確認の大切さを、チームや友だちに体験してもらう
