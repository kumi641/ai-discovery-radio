## 今日の実験

関連ニュース：Qiita：Claude Code の Scheduled tasks（旧名 routines）の入口と基本仕様。作り方、きっかけの種類、上限を公式ドキュメントから整理

#### 実験：明日の朝の「きのうの作業まとめ」を予約する

- **目的**：Claude Code の Scheduled tasks で1回だけの予約を作り、パソコンを閉じていても決まった時間に仕事をしてくれることを確かめる
- **使用ツール**：Claude Code（CLI）、GitHub、claude.ai（Web）
- **必要な準備**：Claude の Pro・Max・Ultra・Team・Enterprise のどれかのプラン、claude.ai のサブスクリプションで Claude Code にログインしておく（API キーでのログインでは /schedule は使えない）、GitHub にある自分のリポジトリ（最近のコミットがあるもの）と、Claude からそのリポジトリへのアクセス
- **所要時間**：約15分
- **費用**：Pro 以上の有料プランが必要（利用量はふだんのセッションと同じように消費）
- **無料の代替**：予約はできないが、同じ依頼文を次の朝にふだんの Claude Code で手動で実行する

**手順**

1. 自分のリポジトリのフォルダで Claude Code を開く
2. 下のコマンドを入力する（時間は、ちょうど0分を避けて9:07のように少しずらす）
3. Claude が時間・リポジトリ・依頼文を確認してくるので、答えてから保存する。最後に表示される実行の日時が、思った時間か確かめる
4. /schedule list を入力して、予約が一覧に出ているか確かめる
5. 次の朝、claude.ai/code/routines でそのタスクを開き、History から実行の記録を開いてまとめを読む
6. うまくいったら、/schedule update で毎週の予約に変えるか考える

**コピーして使うコマンド**

```bash
/schedule tomorrow at 9:07am, read the commits made in this repository yesterday and write a 5-line summary in Japanese, then suggest one next task. Do not change any files.
```
（出典：https://code.claude.com/docs/en/routines）

- **完成するもの**：明日の朝9時すぎに自動で作られる、きのうの作業の5行まとめ
- **確認方法**：次の朝、タスクの History に実行の記録があり、開くと日本語の5行まとめと次の作業の提案が書かれている。実行後、1回だけの予約は Completed になっている
- 参考：https://code.claude.com/docs/en/routines

## 4. Qiita：Claude Code・Codex・claude.ai とスキルで、全12章・約9万字の長編小説を書き上げた記録。設定はファイルを正典にし、字数は実測、点検は別のAIに

**結論**：筆者は約4か月かけて、AI と全12章・約9万字の長編小説を完成させました。記事は作品の中身ではなく、長い仕事を AI に任せながら品質を保つための仕組みと失敗談をまとめています。

> 💡 **こう使うと面白い**：ブログの連載やゲームのシナリオで、設定をファイルにまとめて毎回読ませる仕組みにすると、何話続けても話がぶれずに面白そうです。

### 重要ポイント

- **設定はAIの記憶でなくファイルに**：登場人物や世界の設定を bible/ などのファイルに置き、CLAUDE.md で毎回読むよう指示しました。
- **1章＝1つの会話**：次の章は新しい会話で始める運用で、道具を替えても話がずれなかったそうです。
- **字数はAIの自己申告でなく実測**：AI は目標より短く書きがちなので、コマンドで数え、8割未満なら書き足す手順にしました。
- **点検は別のAIに任せる**：/continuity-check で、読むだけの別の AI に、本文と設定を引用させて矛盾を探させました。

### 技術解説

**何が新しいのか**：Claude Code と Codex を途中で乗り換えても話がずれないよう、作品の事実をすべてファイルに置き、4つのスキル（AI に渡す作業の手順書）で書く・直す・点検する・本にするを分けた点です。

**なぜ重要か**：長い制作では、AI の会話の記憶に頼ると設定を取り違えます。小説に限らず、連載やゲームのシナリオなど、長く続く制作にそのまま使える考え方です。

**従来との違い**：AI に一気に書かせるのではなく、1章ずつ新しい会話で、決まった手順と機械の確認を通して書いています。

- /write-chapter・/polish・/continuity-check・/build-book の4つのスキル
- 推敲は指摘で止め、直すかどうかは作者が選ぶ
- wc -m は UTF-8 の環境でないとバイト数を返し、6,792字の章が20,336と出た失敗
- Claude 用と Codex 用のスキルが食い違ったので、スキルは1か所で管理すべきという教訓

- ブログの連載やシナリオの設定をファイルで管理する

### 重要ポイント

- **お願いでなく仕組みで制限**：書き込める場所やネットの行き先を、システムの設定で区切ります。文章の禁止だけでは確実に守られないためです。
- **調べる会話と書く会話を分ける**：同じ失敗が3回続いたら、指示を直すより /rewind で前の状態に戻します。
- **完了はテスト結果で判断**：AI の「できました」ではなく、テストや型チェックが通ったかどうかで完了とします。
- **分からなければ止まらせる**：不明な点は推測で進めず、選択肢を出して止まるよう依頼文に書きます。

### 技術解説

**何が新しいのか**：エージェント（指示すると自分で手順を考えて作業する AI）を「空気を読む相手」ではなく「与えた範囲で出力する計算機」と考え、制限を文章でなく仕組みに置くという整理です。

**なぜ重要か**：AI を同時にたくさん動かすほど、人が確認する量が増えて追いつかなくなります。完了の判断を機械に任せられる形にすると、人の負担が減ります。

**従来との違い**：よくある「プロンプトをもっと工夫する」対策ではなく、権限・会話の範囲・完了の条件を先に固定する考え方です。

- プロジェクトの外への書き込みを止め、ネットの行き先は許可リストにする
- テストや型の定義を人が先に決め、AI にはその枠の中だけを埋めさせる
- 記事は考え方の提案で、測った数字は載っていない

### 実践アイデア

## 6. Hugging Face、映像と音を一緒に生成する LTX-2.5 を AWS Trainium3 で動かし、ショット表から短編を作る手順と高速化の工夫を公開

### 重要ポイント

- **映像と音を一緒に生成**：LTX-2.5 は Lightricks の約190億パラメータの動画生成モデルで、映像と音を同時に作ります。

### 技術解説

**何が新しいのか**：diffusers の上に約160行の Python を足して、JSON のショット表から、場面のつながりを保った音つきの短編を組み立てる流れを作った点です。最初の試作から、画素数4倍でも計算時間を45秒から15秒に減らしました。
