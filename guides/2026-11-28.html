1. GitHub、Copilot コードレビューの請求先を選んでいない組織は、2026年12月30日から組織への請求が初期設定に

GitHub・公開 2026-11-25 22:18
出典：https://github.blog/changelog/2026-11-25-copilot-code-review-billing-will-default-to-the-organization

結論：GitHub は、Copilot のコードレビュー（AI がコードを読んで問題を指摘する機能）の料金を誰が払うかについて、初期設定を変えると発表しました。請求先を選んでいない組織では、2026年12月30日から組織への請求になります。

重要ポイント

  • 12月30日から初期設定が変更：Copilot のライセンスを持つメンバーのコードレビューについて、請求先の初期設定が変わります。
  • 未設定なら組織に請求：請求先を選んでいない場合、リポジトリを持つ組織に請求されます。組織の支出が増えることがあります。
  • Memberを選べば今のまま：期限までに設定で Member を選ぶと、メンバー自身の利用枠を使う今の形が続きます。

技術解説

何が新しいか
これまでは、請求先が未設定ならメンバー自身の Copilot の利用枠が使われていました。12月30日からは、未設定の場合はリポジトリを持つ組織への請求になります。
なぜ重要か
気づかないままだと、組織の支払いが増えることがあります。組織への請求には、AI クレジットの有料利用を有効にしておく必要があります。
従来との違い
すでに Member か Organization を選んでいる場合は、その設定がそのまま残ります。ライセンスのないメンバー向けの設定は変わりません。
  • 対象は Copilot Business と Copilot Enterprise で、請求先を選んでいない組織と企業
  • AI クレジットの有料利用が無効などの場合は、Member に設定される
  • 企業が設定を管理している場合は、企業のオーナーが選ぶ

実践アイデア

2. Hugging Face と ggml-org、AMD の Ryzen・Radeon で llama.cpp の速さを比べられるダッシュボードを公開

Hugging Face・公開 2026-11-26 11:37
出典：https://huggingface.co/blog/ggml-org/llamacpp-amd-bench

結論：手元のパソコンでAIを動かす道具 llama.cpp が、AMD の部品でどれくらい速く動くかを比べられるページが公開されました。モデル、軽量化の方式、llama.cpp の版ごとに結果を見られます。

💡 こう使うと面白い：部品を買う前に、使いたいモデルがどの軽さでどれくらいの速さで答えを書くかを、このページで確かめておくと失敗が減りそうです。

重要ポイント

  • AMDの機種ごとに速さを比較：Radeon 8060S と Radeon AI Pro R9700S で、モデルや軽量化（量子化）の方式ごとの速さを比べられます。
  • 読む速さと書く速さを測定：PP512 は512語分の質問を読む速さ、TG128 は128語分の答えを書く速さです。どちらも1秒あたりの量で示します。
  • 毎週自動で測り直し、データも公開：公開の GitHub Actions で毎週測り、結果のファイルも誰でも見られます。

技術解説

何が新しいか
決まった機種・決まった手順で毎週自動で測った結果を、版ごとの変化や、会話が長くなったときの速さまで含めて一か所で見られるようになりました。
なぜ重要か
これまでは、ネットの体験談を集めて速さを推測するしかありませんでした。同じ条件で測った数字があると、どのモデルをどの軽さで動かすか決めやすくなります。
従来との違い
個人の測定ではなく、公開された自動の仕組みで、Flash Attention のあり・なしを10回ずつ測っています。
  • llama-bench という測定用の道具で、llama-install.sh で配られている完成版のプログラムを測る
  • Overview・Build history・Context scaling の3つのタブ
  • データは Hugging Face のストレージに「版/機種/モデル/量子化.jsonl」の形で置かれている

実践アイデア

  • パソコン部品を買う前に、使いたいモデルの速さを確かめる
  • 自分の環境で測った速さと比べて、設定が正しいか確かめる
  • エージェントに使う小さなモデルの軽さを選ぶ

3. Qiita：Claude Code の Scheduled tasks（旧名 routines）の入口と基本仕様。作り方、きっかけの種類、上限を公式ドキュメントから整理

Qiita・公開 2026-11-27 17:56
出典：https://qiita.com/akihidem/items/4843f7374f096e9c7e07

結論：Claude Code の Scheduled tasks は、依頼文・リポジトリ・つなぐサービスをまとめて保存し、決まったきっかけで自動で動かす機能です。記事は、旧名 routines を手がかりに入口を見つけ、作り方ときっかけ、上限を公式ドキュメントから整理しています。

💡 こう使うと面白い：毎週月曜の朝に、先週の作業をまとめた報告と今週やることの候補を作らせると、週の始めがぐっと楽になりそうです。

重要ポイント

  • 決まった時間や出来事で自動実行：きっかけは、時間（定期・1回だけ）、API の呼び出し、GitHub の出来事の3種類。組み合わせもできます。
  • PCを閉じていても動く：インターネットの向こうのコンピューターで動くので、手元のパソコンの電源は関係ありません。
  • 旧名routinesが今も残る：/schedule は /routines でも動き、Web の住所も claude.ai/code/routines のままです。
  • 1時間に1回より多くは不可：cron（時間の指定の書き方）は UTC で書きます。毎時の実行回数にも上限があります。

技術解説

何が新しいか
名前が routines から Scheduled tasks に変わり、画面によって表記がまちまちです。記事は、どこに旧名が残っているかと、作るときの注意点をまとめています。
なぜ重要か
自分のパソコンを付けっぱなしにしなくても、毎朝のまとめや週ごとの点検を Claude Code に任せられます。仕組みと上限を知っておくと、思ったとおりに動かないときに迷いません。
従来との違い
/loop やデスクトップの予約タスクは手元のパソコンで動きます。Scheduled tasks はクラウドで動くので、パソコンを閉じていても実行されます。
  • 実行はひとりで進むので、依頼文にやることと成功の条件を全部書く
  • つないでいるサービス（コネクタ）は初期状態で全部含まれるので、いらないものは外す
  • ちょうど0分の指定は数分遅れることがあるので、9:07 のように少しずらす
  • GitHub との接続が切れたまま72時間たつと、タスクは止まる

実践アイデア

  • 毎朝、前日のコミットをまとめさせる
  • 毎週、ドキュメントと実装のずれを点検させる
  • PR が開いたら、自分のチェックリストでレビューさせる

4. Qiita：Claude Code・Codex・claude.ai とスキルで、全12章・約9万字の長編小説を書き上げた記録。設定はファイルを正典にし、字数は実測、点検は別のAIに

Qiita・公開 2026-11-27 21:00
出典：https://qiita.com/tadanok/items/77fa2c7a9d0acd0e3cde

結論：筆者は約4か月かけて、AI と全12章・約9万字の長編小説を完成させました。記事は作品の中身ではなく、長い仕事を AI に任せながら品質を保つための仕組みと失敗談をまとめています。

💡 こう使うと面白い：ブログの連載やゲームのシナリオで、設定をファイルにまとめて毎回読ませる仕組みにすると、何話続けても話がぶれずに面白そうです。

重要ポイント

  • 設定はAIの記憶でなくファイルに：登場人物や世界の設定を bible/ などのファイルに置き、CLAUDE.md で毎回読むよう指示しました。
  • 1章＝1つの会話：次の章は新しい会話で始める運用で、道具を替えても話がずれなかったそうです。
  • 字数はAIの自己申告でなく実測：AI は目標より短く書きがちなので、コマンドで数え、8割未満なら書き足す手順にしました。
  • 点検は別のAIに任せる：/continuity-check で、読むだけの別の AI に、本文と設定を引用させて矛盾を探させました。

技術解説

何が新しいか
Claude Code と Codex を途中で乗り換えても話がずれないよう、作品の事実をすべてファイルに置き、4つのスキル（AI に渡す作業の手順書）で書く・直す・点検する・本にするを分けた点です。
なぜ重要か
長い制作では、AI の会話の記憶に頼ると設定を取り違えます。小説に限らず、連載やゲームのシナリオなど、長く続く制作にそのまま使える考え方です。
従来との違い

5. Zenn：Claude Code を並列で動かすときの破綻は設計の問題。権限の隔離・作業と文脈の分離・テストによる出力ゲートで「間違えられない構造」を作る提案

Zenn・公開 2026-11-27 14:57
出典：https://zenn.dev/kekkai3an/articles/aa8fd0ad67f2b9

結論：筆者は、Claude Code を何体も同時に動かすと確認作業が増えるのは、プロンプトの腕ではなく設計の問題だと主張します。そこで、権限の隔離、作業と文脈の分離、テストによる出力のゲートという3本柱と、依頼文のテンプレートを提案しています。

💡 こう使うと面白い：いつもの依頼文の最後に「分からないときは推測せず、選択肢を出して止まって」と一行足すだけでも、手戻りが減るか試す価値がありそうです。

重要ポイント

  • お願いでなく仕組みで制限：書き込める場所やネットの行き先を、システムの設定で区切ります。文章の禁止だけでは確実に守られないためです。
  • 調べる会話と書く会話を分ける：同じ失敗が3回続いたら、指示を直すより /rewind で前の状態に戻します。
  • 完了はテスト結果で判断：AI の「できました」ではなく、テストや型チェックが通ったかどうかで完了とします。
  • 分からなければ止まらせる：不明な点は推測で進めず、選択肢を出して止まるよう依頼文に書きます。

技術解説

何が新しいか
エージェント（指示すると自分で手順を考えて作業する AI）を「空気を読む相手」ではなく「与えた範囲で出力する計算機」と考え、制限を文章でなく仕組みに置くという整理です。
なぜ重要か
AI を同時にたくさん動かすほど、人が確認する量が増えて追いつかなくなります。完了の判断を機械に任せられる形にすると、人の負担が減ります。
従来との違い
よくある「プロンプトをもっと工夫する」対策ではなく、権限・会話の範囲・完了の条件を先に固定する考え方です。
  • プロジェクトの外への書き込みを止め、ネットの行き先は許可リストにする
  • テストや型の定義を人が先に決め、AI にはその枠の中だけを埋めさせる
  • 記事は考え方の提案で、測った数字は載っていない

実践アイデア

  • いつもの依頼文に、触ってよいファイルと完了条件を書く
  • 並列で動かすときに、テストが通るまで完了にしない
  • 失敗が続いたら会話を巻き戻す

6. Hugging Face、映像と音を一緒に生成する LTX-2.5 を AWS Trainium3 で動かし、ショット表から短編を作る手順と高速化の工夫を公開

Hugging Face・公開 2026-11-27 00:00
出典：https://huggingface.co/blog/video-trainium3

結論：Hugging Face のチームが、AWS の AI 専用の計算機 Trainium3 で、映像と音を一緒に作る AI「LTX-2.5」を動かし、短い映画を作りました。記事は、ショット表で場面をつなぐ作り方と、速くするための工夫を詳しく説明しています。

💡 こう使うと面白い：自分の短い動画の絵コンテを、このショット表の形で書いておくと、場面のつながりを考えながら動画 AI に渡せて面白そうです。

重要ポイント

  • 映像と音を一緒に生成：LTX-2.5 は Lightricks の約190億パラメータの動画生成モデルで、映像と音を同時に作ります。
  • ショット表で場面をつなぐ：ショットごとの説明を JSON の一覧に書き、from で前のショットの最後の場面から、to で次のショットの最初の場面へつなげます。
  • 音つき10秒を約23秒で生成：2048×1024 の音つき10秒の動画を、モデルを読み込んだ後は約22〜23秒で作れました（Trainium3 の半分を使用）。
  • 細部は間違えるので何回か作る：筆者たちは、1ショットにつき4回ほど作って選ぶ作り方を勧めています。1ショットは最大20秒です。

技術解説

何が新しいか
diffusers の上に約160行の Python を足して、JSON のショット表から、場面のつながりを保った音つきの短編を組み立てる流れを作った点です。最初の試作から、画素数4倍でも計算時間を45秒から15秒に減らしました。
なぜ重要か
動画 AI は、1本ずつ作ると場面ごとに雰囲気がばらばらになりがちです。前の場面の終わりから次を始める作り方は、話のつながった映像を作るときの基本の型になります。
従来との違い
1つのプロンプトで1本作るのではなく、決めの場面を先に作り、その前後を作っていく「ポーズ・トゥ・ポーズ」の順番も使っています。
  • モデルを4つのコアに分けて載せ、さらに映像を8つに分けて計32コアで計算
  • 文字の読み込みを約205秒から1.4秒に短縮するなど、計算機側だけでなく準備側も速くした
  • モデルの読み込みに約3分、最初の1本に約80秒かかるので、サービスにするならプロセスを動かしたままにする

実践アイデア

  • 自分の短い動画の絵コンテを、ショット表として書いておく
  • 前の場面の最後から次を作る流れを、ほかの動画 AI でも試す
  • 1ショットを何回か作って選ぶ前提で、制作の時間を見積もる
