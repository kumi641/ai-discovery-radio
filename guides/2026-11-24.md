## 今日の実験

関連ニュース：Hugging Face「How to build and maintain an agentic evaluation」：エージェント評価の作り方と保ち方

#### 実験：AI作業に小さなテストを作る

- **目的**：いつもAIに頼む作業に合否チェックを作り、採点が正しいかを確かめてから、AIを3回走らせて安定して成功するかを見る
- **使用ツール**：Claude Code（または Claude などのAIチャット）、Python
- **必要な準備**：Python が動く環境、AIに頼みたい小さな作業を1つ（例：CSVの列を並べ替えて保存する）、作業用の空のフォルダ
- **所要時間**：約45分
- **費用**：無料枠で可能（Claude Code を使う場合は利用中のプランの範囲）
- **無料の代替**：Claude の無料プランのチャットで check.py を作らせ、手元の Python で動かす

**手順**

1. 作業を1つ決め、合格条件を「AIの返事」ではなく「できたファイルの中身」で書き出す
2. 下のプロンプトで、合否を判定する check.py をAIに作らせる
3. お手本の答えを自分で用意し、check.py で合格になるか確かめる
4. 何もしない状態（ファイルなし）と、近道の答え（見た目だけ合わせたもの）が不合格になるか確かめる。合格してしまったら check.py を直す
5. AIに同じ作業を3回、毎回新しい会話で頼み、それぞれ check.py で判定する
6. 3回中何回合格したか、3回とも合格したかを記録する

**コピーして使うプロンプト**

```
これから、AIに頼む作業の合否を判定する Python スクリプト check.py を作りたいです。
作業：「（ここに作業を書く。例：input.csv の列を日付の順に並べ替えて output.csv に保存する）」
条件：
- AIの返事ではなく、作業後のファイルの中身だけで判定する
- 合格なら PASS、不合格なら FAIL と理由を1行で表示する
- 次の3つで判定が正しいか確かめられるよう、お手本の答え・何もしない状態・近道の答え（見た目だけ合わせたもの）の作り方も説明する
まだ作業そのものは行わず、check.py とその説明だけを書いてください。
```

- **完成するもの**：check.py と、お手本・何もしない・近道・AI3回分の判定結果の表
- **確認方法**：お手本だけが PASS、何もしない状態と近道が FAIL になり、AI3回分の結果が表に記録されている
- 参考：https://huggingface.co/blog/agentic-evals

## 3. Hugging Face「How to build and maintain an agentic evaluation」：エージェント評価の作り方と保ち方

*エンジニアの実践ノウハウ｜Hugging Face・公開 2026-11-23 00:00｜評価 89/100*

**結論**：Hugging Face が、AIエージェントの評価（テスト）の作り方と保ち方をまとめました。課題、環境、採点役などの部品に分け、採点そのものが正しいかを確かめる手順を示しています。

> 💡 **こう使うと面白い**：毎回 AI に頼んでいる作業に、合否を自動で判定するチェックを一つ作り、3回続けて合格するかを見ると、任せてよい作業が分かって面白いです。

### 重要ポイント

- **結果の状態で採点する**：エージェントの「できました」という言葉ではなく、作業後のファイルや環境の状態を採点役が確かめる。
- **正解役・何もしない役で検査**：お手本の解き方は必ず合格し、何もしないエージェントは必ず不合格になるかを先に確かめる。
- **ずるで通らないか確かめる**：記事の例では、近道の答えが比率だけを見る採点に全問合格したため、採点をもっと細かくした。
- **毎回成功するかも測る**：3回中1回でも成功すればよい指標と、3回とも成功する指標を分ける。例では前者が8問中7問、後者は1問だった。

### 技術解説

**何が新しいのか**：お手本・何もしない・近道の3種類で採点役を先に検査する、という具体的な手順と、実際の物理実験の課題での失敗例が示されたことです。

**なぜ重要か**：採点が甘いと、AIが本当はできていないのに「できた」と判定されます。放っておいて任せる作業ほど、毎回成功するかが大事になります。

**従来との違い**：従来は、AIの最終的な返事の文章を見て採点しがちでした。この記事では、作業後の状態を確かめ、採点役自体も検査します。

- 課題・エージェント・環境・記録・採点役に分けて考える
- お手本は合格、何もしないは不合格、近道も不合格を確認
- 失敗の記録を原因ごとに分ける
- pass@k と pass^k を分けて報告する

- 自作エージェントの改善前後の比較
- プロンプトを変えたときの成功率の比較

## 4. AIに「公開しないで」と頼むより、MCPサーバーから公開の操作そのものを外した設計（OAuth×Supabase）

*エンジニアの実践ノウハウ｜Zenn・公開 2026-11-23 15:54｜評価 78/100*

出典：https://zenn.dev/murzim/articles/f5066afd82976c

**結論**：Webツールのマーケットプレイスで、AIが出品の下書きを作れるリモートMCPサーバーを作った記録です。公開だけはさせないため、公開のツール自体を用意せず、データベースの側でも公開の項目に書けないようにしました。

> 💡 **こう使うと面白い**：自分のAIに渡している道具を一覧にして、「消す」「送る」「公開する」の操作を外すか下書き止まりにすると、安心して任せられる範囲が広がります。

### 重要ポイント

- **頼むより、手段を持たせない**：プロンプトでのお願いは、AIが読む文章に紛れた指示で破られるおそれがあるため、仕組みの側で防いだ。
- **公開用のツールを作らない**：6つのツールは読み取り3つと書き込み3つ。下書きは作れるが、公開は出品者が画面で行う。
- **公開に関わる入力はエラーに**：status や publish などの項目が来たら拒否し、日本語のエラーでAIが自分で直せるようにした。
- **別のAIにレビューを依頼**：実装は Claude Code、レビューは Codex。指摘は 12→5→1→7→4→0 件と減っていった。

### 技術解説

**何が新しいのか**：AIの行動を言葉で制限するのではなく、AIが使える道具の一覧から危ない操作を外し、何重にも防ぐ具体例です。

**なぜ重要か**：AIに書き込みの権限を渡すと、お願いだけでは守られないことがあります。手段を持たせない設計なら、うっかりや悪意のある指示でも事故が起きにくくなります。

**従来との違い**：プロンプトで「〇〇しないで」と書く方法に比べ、そもそもその操作ができない作りにしている点が違います。

- MCP専用のトークンを発行し、データベースの鍵は渡さない
- 保存用の関数は公開の状態を下書きのまま固定
- 公開に関わる項目の入力をエラーにする
- OAuth 2.1 と PKCE でログインし、パスワードを貼らせない

### 実践アイデア

- 自作のMCPサーバーで、削除や送信のツールを外す
- AIに下書きまでを任せ、最後の確定は人がする仕組み
- AIに渡す道具の一覧の見直し

#### 今日すぐできること：AIに渡す道具の棚卸し

- **目的**：自分のAIが使える危ない操作を見つける
- **使用ツール**：Claude などのAIチャット
