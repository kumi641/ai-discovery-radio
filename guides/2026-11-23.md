- **必要な準備**：Claude Code をインストールしてログインしておく、claude --version で v2.1.232 以降か確認する（終わったら知らせる機能は v2.1.236 以降）、同じパソコンでターミナルを2つ開く（コンテナの中と外ではつながらない）
- **所要時間**：約15分
- **費用**：課金が必要（Claude Code が使える有料プランか API。届いたメッセージも通常の入力と同じく利用量に数えられる）
- **無料の代替**：Claude Code の無料枠は未確認（公式の料金ページで確認）。費用を抑えるなら短い伝言を数回だけ送る

**手順**

1. ターミナルBで claude を起動し、/rename worker-b と打って名前を付ける
2. ターミナルAで claude を起動し、/list-agents を打って worker-b が一覧に出るか確かめる
3. ターミナルAで下のプロンプトを送る（@ と打って worker-b を候補から選ぶ）
4. ターミナルBに『Message from @…』という薄い一行が届くか見る。Ctrl+O で全文を読む
5. ターミナルBに何か作業を頼んでから、Aで『worker-b の作業が終わったら教えて』と頼み、知らせが届くか確かめる
6. 終わったら、/config の『Messages from your other sessions』で受け取り方（accept / hold / refuse）を確認する

**コピーして使うプロンプト**

```
@worker-b に、こちらの作業の結果を3行でまとめて伝えてください。相手に何かを実行させたり、設定を変えさせたりする依頼は入れないでください。
```
（出典：https://code.claude.com/docs/en/cross-session-messaging）

- **完成するもの**：セッションAからBへ届いた伝言と、作業終了の知らせ
- **確認方法**：ターミナルBの会話に Message from の一行が表示され、Ctrl+O の画面で全文が読める。終了の知らせがAに届く

## 1. OpenAI、AIの進歩を比べる共通の物差しとして perplexity（次の言葉の当てにくさ）を使おうと提案し、社内の数値を公開

*最新AIニュース｜OpenAI・公開 2026-11-22 00:00｜評価 53/100*

出典：https://openai.com/index/perplexity-and-intelligence

**結論**：OpenAI の研究責任者 Jakub Pachocki 氏が、AI の進歩を比べる共通の物差しとして perplexity を使うことを提案しました。社内のプログラムの文章で測った数値を公開し、数値が下がるにつれてどんな力が現れたかを説明しています。

### 重要ポイント

- **進歩を測る共通の物差しを提案**：perplexity は、AI が次に来る言葉をどれだけ迷わず当てられるかを表す数字。小さいほど良く当てられる。
- **社内の数値を初めて公開**：社内のプログラムの文章で測った数値と、各モデルでできるようになったことを並べて公開した。
- **力の現れ方は事前に読めない**：筆者は、新しい力がいつ現れるかは前もってはっきり分からなかったと書いている。
- **越えない線を各社で決めようと提案**：安全を見守る仕組みが追いつくまで、各社で越えない数値の線を決めようと呼びかけている。

### 技術解説

**何が新しいのか**：これまで社内だけで持っていた perplexity の数値を、ある時点の分について公開した点です。新しい道具やデータの公開はありません。

**なぜ重要か**：AI の力は細かい試験の点数で語られがちですが、学習のもとになる予測の上手さという一つの数字で進み方を追えば、全体の速さが見えやすくなる、という主張です。安全のルールづくりにも使おうとしています。

**従来との違い**：個別の試験の点数ではなく、事前学習（大量の文章から次の言葉を当てる練習）の段階の数値に注目します。ただし会社ごとにデータが違うため比べにくい、実際の仕事の上手さと直接は結びつかない、などの限界も本人が挙げています。

- perplexity は、まだ見せていない文章で次の言葉を予測させたときの外れにくさを表す
- GPT-4 の頃に、順を追って考える力が役立つようになったと説明している
- 順を追って考える工夫のように、事前学習の外で伸びた力はこの数字に表れないと認めている

## 2. Zenn：Claude Code に同じ修正を何通りも試させる agent-mcts。課題文から先にテストを書かせると20回中16回で改善、あいまいなバグ報告では失敗し v0.4.1 で対策

*エンジニアの実践ノウハウ｜Zenn・公開 2026-11-22 19:28｜評価 81/100*

出典：https://zenn.dev/natsu529/articles/ef09f78c0dde1d

> 💡 **こう使うと面白い**：仕様がはっきりした小さな関数づくりで、一回だけ頼んだ答えと、何通りも試させた答えを並べて比べると、AI に任せるときの頼み方のコツが見えてきて面白そうです。

### 重要ポイント

- **答えを木のように枝分かれで探す**：agent-mcts は Claude Code の1回の作業を木の1つの枝として扱い、よさそうな枝に予算を回す。
- **先に確認用テストを別AIが作る**：答えを見せずに、課題文と元のコードだけから別のエージェントがテストを書くので、答えに合わせたテストになりにくい。
- **20回中16回で一回目より良く**：作者の計測（haiku、課題2つ、各20回）で、最初の答えより良くなったのが16回、悪くなったのが2回。
- **あいまいなバグ報告では失敗**：テストを書く AI もバグと同じ勘違いをして、直す前のコードを選んだ。v0.4.1 で元からあるテストを優先する規則にした。

### 技術解説

**何が新しいのか**：`--generate-tests` で、探索の前に別のエージェントが課題文と元のコードだけを見てテストを書き、その結果で答えを採点・修正するようにした点です。

**なぜ重要か**：AI に一回だけ頼むより、落ちたテストを見せて直させるほうが答えが良くなる、という傾向を数字で示しています。作者は、伸びた主な理由は『選ぶこと』より『直すこと』だったと分析しています。

**従来との違い**：AI に差分を読ませて点を付ける `--judge` は平均では伸びましたが、その大半は壊れていた最初の答えを直した2回の分でした。生成テストのほうが安定して良くなりました。

- 各候補は git worktree（同じリポジトリの別の作業場所）と、分岐させたエージェントの会話でできている
- 採点は、プロジェクトのテストと生成テストの通過率を半分ずつ合わせる
- v0.4.1 では、プロジェクト自身のテストで悪化していない答えの中から最高点を選び、それ以外の指標だけが修正前を推したら警告する
